# Zerek AI — видеоаналитика для малого бизнеса на уже установленных камерах

> **ҚАЗ.** Zerek AI дүкендегі, кафедегі, салондағы, ХҚКО мен АЖС-тағы бар камераларды «зерек көмекшіге» айналдырады:
> келушілер ағынын санайды, кезекті, бос қалған кассаны, клиентке ешкім жақындамағанын байқап,
> иесіне Telegram арқылы хабарлайды. Бет-әлпетті тану қолданылмайды.
>
> **ENG.** Zerek AI turns the cameras a small business already has — shops, cafés, salons, service centres,
> petrol stations — into an attentive assistant: it counts
> visitors, spots queues, an unattended till or a customer nobody has approached, and alerts the owner in
> Telegram. No face recognition. Built for Digital Taraz Hackathon (Zhambyl Hub), track
> *AI for SME & Local Business*.

**Zerek** (каз. «зерек») — сообразительный, внимательный. Для любого бизнеса, где клиента надо вовремя
встретить и обслужить: магазины и аптеки, кафе и рестораны, салоны, ЦОНы, банки, АЗС. Первый MVP — продуктовый
магазин; кафе и одежда уже описаны конфигами. Ядро общее, отрасль задаётся **только конфигом** (зоны,
линии, объекты с состояниями, правила) — новый YAML, а не новый код.

```
видео/RTSP → RF-DETR (люди) → BoT-SORT (треки) → роль сотрудник/клиент
          → зоны · линии · время в зоне · контакт → машины состояний + правила
          → SQLite (события) · Telegram/консоль (оповещения) · отчёт · видео с оверлеем
```

| Слой | Готовое решение | Лицензия |
|---|---|---|
| Детектор людей | [RF-DETR](https://github.com/roboflow/rf-detr) Medium, COCO `person` | Apache-2.0 |
| Трекинг | [Roboflow trackers](https://github.com/roboflow/trackers) — BoT-SORT (с компенсацией движения камеры), ByteTrack, OC-SORT | Apache-2.0 |
| Детекции/аннотации | [supervision](https://github.com/roboflow/supervision) | MIT |
| Всё остальное | свой код: `storevision/` | — |

## Запуск

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
./scripts/get_data.sh                     # демо-видео + CAVIAR + Mall + PoseLift (MERL: ./scripts/get_data.sh merl)
.venv/bin/python -m storevision.run configs/grocery_checkout.yaml          # кассы
.venv/bin/python -m storevision.run configs/grocery_checkout.yaml --cctv   # то же, качество регистратора
.venv/bin/python -m storevision.run configs/grocery_aisle.yaml             # проход
.venv/bin/python -m storevision.run configs/caviar_entrance.yaml           # вход, настоящая CCTV
.venv/bin/python tools/eval_caviar.py                                      # точность счётчика по разметке
.venv/bin/python -m pytest -q tests                                        # 16 сценариев логики
```

Результат: `out/<site>/<raw|cctv>/` — `*.mp4` с оверлеем, `events.db`, `report.json`, `alerts/*.jpg`
(кадр к каждому оповещению). Детекции кэшируются в `out/cache/` — пороги и зоны можно менять и
перезапускать за секунды.

Telegram: `output.telegram.enabled: true` + переменные окружения `TG_BOT_TOKEN`, `TG_CHAT_ID`.

## Живой режим: Frigate + RTSP + дашборд

```
камеры ──RTSP──► Frigate 0.18 (go2rtc :8554, запись 24/7 в frigate/storage)
                    │ рестрим rtsp://127.0.0.1:8554/<камера>
                    ▼
           storevision.live — поток на камеру, переподключение, общий RF-DETR
                    │ события → SQLite (WAL)      оповещения → кадр + ссылка на клип Frigate
                    ▼
           дашборд http://127.0.0.1:8088 (FastAPI + одна страница)
```

```bash
docker compose up -d                 # Frigate: http://127.0.0.1:5000 (UI/архив), go2rtc: :1984
./scripts/live.sh                    # анализ + дашборд на :8088 (configs/live_demo.yaml)
```

Сейчас «камеры» — три демо-ролика, которые go2rtc крутит по кругу (`#input=loop`). Подключить
реальную камеру:

1. `frigate/config/config.yml` → `go2rtc.streams`: `kassa: rtsp://admin:{FRIGATE_RTSP_PASSWORD}@192.168.1.64:554/Streaming/Channels/102`
   (пароль — переменная окружения `FRIGATE_RTSP_PASSWORD`, в конфиг не пишется) и такая же камера в `cameras:`;
2. `configs/live_demo.yaml` → камера с `source: rtsp://127.0.0.1:8554/kassa`, `frigate_camera: kassa`, зоны по кадру;
3. `docker compose restart frigate && ./scripts/live.sh`.

Дашборд: показатели за период (1 ч / сегодня / 7 дней), кассы и зоны «сейчас» со статусами,
входы покупателей по интервалам, ожидание без обслуживания по сотрудникам (медиана + p90 + нагрузка),
живые камеры с разметкой анализа, лента оповещений с кадром и клипом из архива Frigate. API:
`/api/state`, `/api/stats?range=`, `/api/alerts`, `/api/stream/<камера>` (MJPEG).

## Схема конфига (`storevision/config.py`, JSON Schema — `configs/schema.json`)

| Блок | Что задаёт |
|---|---|
| `site` | id, название, отрасль (`grocery`, `cafe`, `fashion`, …), часовой пояс |
| `cameras[]` | источник (файл/RTSP), `process_fps`, `anchor` (`bottom` — ноги, для камеры сверху; `center` — для камеры на уровне глаз), `zones[]` и `lines[]` в долях кадра |
| `zones[].kind` | `staff_area`, `queue`, `service`, `table`, `fitting_room`, `shelf`, `storefront`, … |
| `lines[]` | счётчик проходов; `hysteresis` гасит двойной счёт на пороге; персонал не считается |
| `staff` | `uniform` — HSV-цвет формы на торсе; `zone` — кто ≥ N с в staff-зоне, тот сотрудник |
| `machines` | шаблоны машин состояний (касса, стол, зона помощи) с переходами и оповещениями по времени в состоянии |
| `objects[]` | экземпляры: «Касса 1», «Стол 5» — подставляют реальные зоны в `$плейсхолдеры`, `owner` = кто отвечает (секция/смена) |
| `rules[]` | глобальные правила: условие + `for_s` (держится N с) + `cooldown_s` + шаблон сообщения |

**Условия** (одинаковые для правил и переходов):
`occupancy` (сколько клиентов/сотрудников в зоне), `dwell_max` (дольше всех в зоне),
`contact` (сотрудник у объекта ≥ N с с момента входа в состояние), `time_in_state`, `all/any/not`.

**Шаблоны сообщений**: `{queue_1.customer}`, `{queue_1.staff}`, `{queue_1.dwell}`, `{duration}`,
а в объектах ещё `{object}`, `{owner}`, `{wait}`.

Примеры: `grocery_checkout.yaml` (касса: нет клиентов → обслуживание / клиент ждёт без кассира),
`cafe_example.yaml` (стол: свободен → ждут первого подхода → обслуживаются → давно не подходили →
нужна уборка), `fashion_example.yaml` (зона помощи: смотрят → ждёт консультанта → консультант рядом).

| Скорость | Apple M4, MPS | RF-DETR Medium ≈ 76 мс/кадр 1280×720 → ~13 к/с на одну камеру |

Найденные и исправленные проблемы: ноги закрыты кассой/тележкой → `anchor: center`; топтание на
пороге даёт двойной счёт → `hysteresis`; мигание точки на границе зоны дробит визит → выход из зоны
засчитывается через 1 с; у камеры с другим зумом своя линия двери.

## Честные ограничения

* Pexels и Supervision — **стоковая съёмка с рук**, не CCTV: годится показать конвейер, не мерить точность.
  Режим `--cctv` эмулирует регистратор (960 px, сильное сжатие). В нём на кассах один ложный переход
  «клиент ждёт без кассира», когда прохожий перед камерой закрыл кассира — на проде гасится `for_s: 10`.
* Сценарий «касса без кассира» на реальном видео не показан — в доступных роликах кассир всегда на месте.
  Логика проверена тестами; на реальном видео — нужна запись из пилотного магазина.
* Трек рвётся при долгом перекрытии → время в зоне начинается заново. Следующий шаг — ReID-эмбеддинги
  (BoT-SORT с ReID) или правило «зона занята непрерывно».
* Идентификация конкретного сотрудника — по секциям/сменам (`owner`), без лиц.

### Результаты на датасетах

**Mall — подсчёт людей** (`tools/eval_mall.py`; сплит литературы: кадры 1–800 подбор порога, 801–2000 тест)

| Вариант (порог подобран на 1–800) | Тест-кадров | MAE ↓ | RMSE | Смещение | Отн. ошибка |
|---|---|---|---|---|---|
| RF-DETR Medium, порог 0,20 (первый прогон, перебор упёрся в край) | 1200 | 6,13 | 7,35 | −5,5 (недосчёт) | 19,0 % |
| RF-DETR Medium, порог 0,15 | 1200 | 4,67 | 5,93 | −0,1 | 14,5 % |
| то же, на тех же кадрах, что SAHI | 240 | 4,62 | 5,77 | −0,7 | 14,3 % |
| **RF-DETR Medium + SAHI 2×2** (`supervision.InferenceSlicer`) | 240 | **3,06** | 3,78 | +0,4 | **9,5 %** |

Для сравнения (таблица [DecideNet, arXiv 1712.06679](https://arxiv.org/pdf/1712.06679)): детекторы,
обученные на Mall, — Faster R-CNN 5,91, R-FCN 6,02; модели подсчёта толпы (регрессия/плотность) —
1,5–2,8. Готовый RF-DETR без дообучения с нарезкой кадра лучше этих детекторов, но хуже
специализированных счётчиков толпы. Нарезка стоит ~4× времени: для живого режима — только на
камерах с толпой (вход, кассы в час пик). Ошибка без нарезки неравномерна: при 13–25 людях
перебор (9,3 — ложные срабатывания при низком пороге), с нарезкой ровно ~3 при любой плотности.

**SAHI-нарезка на счётчике двери** (`tools/eval_caviar.py --slice on|off`; CAVIAR, 7 роликов, 26 событий)

| Вариант | Ошибки входа/выхода | Время прогона |
|---|---|---|
| **без нарезки** | **2 из 26 (8 %)** | 365 с |
| SAHI 2×2, подавление дублей по IoU | 5 из 26 (19 %) | 1487 с |
| SAHI 2×2, по IOS | 20 из 26 (77 %) | 1483 с |

Нарезка помогает считать мелких людей в толпе (Mall), но вредит счётчику прохода: рамки на стыках
плиток дробятся, трек рвётся, появляются «призраки», пересекающие линию. Поэтому в живом режиме
`slicing` — настройка камеры, а на камере входа она выключена.

**MERL Shopping — «рука у полки»** (`tools/eval_merl.py`; порог — на субъектах 10–15, тест — 10 роликов
субъектов 27–33, 3 к/с). Положительный кадр = «тянется к полке» ∪ «убирает руку» ∪ «рука в полке».
Признак — самая верхняя уверенная кисть (RF-DETR Keypoint), порог y < 0,52 высоты кадра.

| Метрика | Значение |
|---|---|
| F1 на тесте (4251 кадр) | **0,725** (точность 0,70, полнота 0,75) |
| Базовая линия «всегда у полки» | F1 0,496 |
| Разброс по роликам | 0,58–0,83 |

Авторы MERL меряют иначе (AP по отдельным действиям с B-LSTM: 92 % «тянется», 70 % «рука в полке»),
поэтому напрямую не сравнимо. Это примитив «покупатель взаимодействует с полкой» для метрик полки и
как вход для детектора краж. Модель поз — 350 мс/кадр на M4: для живого режима нужна лёгкая.

**PoseLift — кражи по позам** (протокол STG-NF: train — только обычные покупки, test — 47 роликов,
4846 кадров, 32 % кадров с кражей). Сравнение на **одном протоколе**: STG-NF обучен у нас кодом авторов
PoseLift (`research/stgnf/run_stgnf.py`, их параметры по умолчанию: окно 24, 8 эпох, 5 сидов, CPU), а наш
kNN подсчитан их же функцией (`tools/eval_poselift.py` → `ours_global_authors_protocol`): оценка окна —
в центральный кадр, по людям — максимум подозрительности, сглаживание Гауссом σ=1…6.

| Модель | AUC-ROC ↑ | AUC-PR, норма = «+» (как у авторов) | AUC-PR, кража = «+» | EER ↓ |
|---|---|---|---|---|
| **kNN по позам, окно 12** (без нейросети) | **72,3** | **87,5** | **45,1** | **0,34** |
| kNN по позам, окно 24 (проверка устойчивости) | 70,3 | 86,1 | 44,1 | 0,35 |
| STG-NF, 5 сидов: среднее ± σ | 65,7 ± 2,4 | 83,5 ± 1,2 | 41,0 ± 2,4 | 0,40 ± 0,03 |
| STG-NF: лучший / худший сид | 68,2 / 62,9 | 84,6 / 82,2 | 44,0 / 38,7 | 0,37 / 0,44 |
| STG-NF в статье (для справки) | 67,5 | 84,1 | — | 0,39 |
| случайный уровень | 50 | 68,3 | 31,7 | 0,5 |

Выводы:
* **AUC-PR в статье считается с «нормой» как положительным классом** (`clip_gt = 1 − clip_gt` в
  `utils/scoring_utils.py`), его случайный уровень — 68, а не 32. Поэтому прежнее сравнение «наши 43,8
  против 84,1» было некорректным: та же модель STG-NF даёт 82–85 в конвенции авторов и 39–44 — в обычной.
* Наш STG-NF воспроизводит статью (67,5 / 84,1 попадают в разброс сидов, ближе к лучшему).
* Простой kNN на одном протоколе не хуже STG-NF и выше всех 5 сидов, в том числе с окном 24 (выбрано
  авторами заранее, а не нами). Но парный бутстрэп по роликам: ΔAUC-ROC = +6,6, 95 % ДИ [−7,2; +23,7],
  P(Δ ≤ 0) = 0,16 — **на 47 тестовых роликах разница статистически не доказана**.
* Изменения в коде авторов — только совместимость: стиль matplotlib `seaborn-ticks` →
  `seaborn-v0_8-ticks`, `np.int/np.float` → `int/float` (NumPy 2), обучение на CPU (MPS не держит float64).
  Ось (y, x) в данных оставлена как у авторов; наш kNN переставляет её сам.

Главный набор для пилота — 2–3 дня записи с регистратора пилотного магазина + ручная разметка
(«сел/подошёл», «встал в очередь/обслужен», входы). Метрики: ошибка счётчика ≤ 5% против ручного
подсчёта за 2 ч; точность оповещений ≥ 80%; ложные тревоги на камеру-час.
